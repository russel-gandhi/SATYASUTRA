## Goal

Phase 2's first gate sentence: the same text twice returns the cached verdict. Today the fast clock has a result cache but `POST /verify` does not use it, so a repeat still calls Gemini and the Fact Check API.

## Done when

- `POST /verify` consults a cache before extraction. The key is the normalised text key from the fast clock (`text_key`), so case, URLs, whitespace and Unicode forms do not defeat it. A hit returns the stored result with `from_cache: true`, the time the verdict was made and the age of its evidence, and **calls neither Gemini nor Fact Check** (asserted by counting requests to the local servers in `tests/unit/test_verify_cache.py`).
- A cache hit still counts toward the cluster's velocity and does not write a second ledger row; the response points to the original `ledger_seq`.
- The time-to-live comes from config. It is **shorter for `UNVERIFIABLE_YET`** than for a decided verdict, because new fact-checks appear (state the two values and why in `config/runtime.yaml`). A failed run (extraction error, outage) is **never cached**.
- Concurrent identical requests produce one upstream call, not two (a test sends several at once).
- `from_cache` and the age are visible to the person reading the result; a stale hit is marked, not hidden (the existing `STALE_SOURCE` flag stays on the decided verdicts it applies to).
- The p95 time from request to cached verdict is measured on this machine over 50 repeats and recorded in the closing evidence against the < 1 s target of Bible Part 3.1.
- `tests/contract/test_walking_skeleton.py` gains a live case: the same statement twice, the second answered from cache with the same `ledger_seq`.

## Notes

Cache the final result of a request, not the Gemini reply, so a rule change is picked up when the entry expires. Record the code version in the cache entry and treat an entry from a different `config_checksum` as a miss; otherwise a changed threshold would keep serving old verdicts.
